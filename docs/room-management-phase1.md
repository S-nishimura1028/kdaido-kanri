# 部屋管理 第1工程｜部屋マスタ設計・現行台帳の照合

作成日: 2026-10-26  
対象: 熊本大同青果 備品管理システム（Supabase / Vercel）  
状態: **設計・登録候補の整理完了／DB変更・使用者紐付けは未実施**  
設計原則: **見取り図を作らず、一覧 → 部屋詳細 → 備品確認の順に扱う**。

## 1. 第1工程の目的と対象外

- 建物単位で部屋を識別するための、変更しにくい部屋マスタを設計する。
- 既存の「使用者マスタ」「備品台帳」と、部屋の物理的所在を区別する。
- 部屋番号・階・和室の候補を整理し、確認すべき不一致を洗い出す。
- 利用者に表示する情報は**管理者ログイン時のみ**に限定する。

**この工程では行わないこと:** roomsテーブル新設SQLの実行、asset_users/ assetsの更新、居住者の自動割当、備品の部屋への自動割当、退去処理の変更、デモ画面への個人情報の表示。

## 3. 承認予定のデータモデル（第1工程では未実行）

### public.rooms（部屋マスタ）

| 列 | 型・ルール | 用途 |
|---|---|---|
| id | UUID PK | 将来の部屋参照で使う内部ID。部屋番号変更でも維持 |
| location_id | UUID FK→locations.id | 建物・寮の識別。異なる寮の「101」の衝突を防ぐ |
| room_code | text NOT NULL | 「101」「南側和室」などの表示上の部屋コード |
| display_group | text NOT NULL | 一覧表示グループ「1階」「2階」「和室」 |
| floor_level | integer NULL | 実際の階数。和室は確認までNULL |
| room_kind | 'numbered' / 'japanese' | 番号付き個室、和室の区別 |
| display_order | integer NOT NULL | 管理者が見る並び順 |
| capacity | integer NULL | 定員。推定値を入れず未確認はNULL |
| approval_status | draft / confirmed / archived | マスタの確認状態。入居状態とは独立 |
| notes | text NULL | 個人名を記載しない運用メモ |
| created_at / updated_at | timestamptz | 登録・更新日時 |

UNIQUE(location_id,room_code) で同じ寮の重複登録を防ぐ。マスタ自体に「入居者名」「空室フラグ」「現物確認済みフラグ」は格納しない。

### 将来連動するときの考え方（第2工程以降）

- **部屋と入居者は別テーブル** room_assignments(room_id,asset_user_id,started_at,ended_at)で管理する。1部屋に複数人の可能性を残し、使用者が同時に2室へ入居することは制約で防ぐ。過去の在室履歴を残せる。
- asset_usersの現行 location / room_number はすぐに消さず、管理者確認後に room_assignments へ段階移行する。
- **備品の所在は入居者の居住部屋と同一とは限らない。** 物理的な配置を確認してから assets.room_id 等に紐付ける。「使用者が101に住むので、貸出品もすべて101にある」と自動推定して更新するのは禁止。
- 退去・回収は既存の asset_exit_sessions / asset_exit_items を主系として維持し、部屋表示はその進捗を参照する。別の退去確定処理を並立させない。
- 棚卸し進捗は「room_inventory_sessions / room_inventory_items」等で実際の点検操作を記録し、マスタのapproval_statusと混同しない。

## 4. ペルソナ別UI要件

| ペルソナ | 最初に見たい情報 | 一覧に必要な動線 |
|---|---|---|
| スマホで現物確認する担当 | 部屋番号、未確認数、今いる部屋 | 大きな部屋カード → QR/現物確認 |
| 退去を処理する担当 | 誰が退去予定か、残る貸出物 | 部屋詳細 → 使用者 → 既存の退去・回収チェック |
| 総務・管理責任者 | 建物ごとの進捗・不明データ | 寮選択 → 未確認を優先表示 → 該当詳細 |
| 新任管理者 | 状況ラベルの意味と次の操作 | 目的別の案内、保存前の確認、エラー時の再試行 |

**一覧カードの優先順**：①部屋名・階　②入居状況（確認済み/未確認ではなく「入居中/空室/要確認」）　③備品の点検状態（未確認/確認途中/確認済み）　④備品件数　⑤詳細ボタン。

入居状況と点検状況には**別ラベル・別色**を使う。判定材料がない場合は空室・確認済みを推測で表示しない。PCは建物/階の一覧と選択部屋の詳細を並列表示し、スマホは一覧→詳細の1列遷移。

## 5. 今回決めること・保留すること

### 基本方針（設計確定）
1. 部屋の主キーはUUID、建物は既存locationsマスタと紐付け。
2. 表示は一覧型、見取り図は作らない。
3. 部屋・使用者・備品は別エンティティにして自動連動しない。
4. 実データを変更する処理は管理者のみ。新設テーブルはRLSを必須とする。
5. 個人名・具体的な入居割当はGitHub/公開デモに入れない。

### 要確認（現場での照合・承認）
- 201・206・208が現在の管理対象として存在するか、入居状況はどうか。
- 203・204など欠番の意味（実際に存在しない/使用しない/未登録）。
- 南側和室・北側和室の実際の階数・位置と定員・共用区分。
- 205の使用者部署入力「205」の正式な部署名。
- 薄場寮で部屋未設定の有効使用者2件の扱い（実際の入居者か部署単位の管理用レコードか）。
- 部屋まで結び付けられない備品12件の現物所在。台帳に存在するだけでは部屋配備と判定しない。
- 他の寮（城山寮・八島寮・春日団地等）へ展開する範囲と順序。
